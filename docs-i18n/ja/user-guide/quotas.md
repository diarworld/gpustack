# クォータ { #quotas }

「Usage」ページの「Overview」にある**Limits**セクションには、ゲートウェイが現在あなたのトラフィックに適用しているクォータが表示されます。各上限のどれだけを使ったか、各ウィンドウがいつリセットされるか、そして週次・月次予算についてはリセットボタンも表示されます。このセクションは常に自分自身のみを対象とし、管理者には管理者自身の limits が表示されます。

![Usage quotas](../assets/usage/usage-quotas.png)

## 上限カード { #the-limit-cards }

各カードには「使用量 / 上限」の値、プログレスバー、リセットまでのカウントダウンが表示されます。カードの`?`アイコンは、そのウィンドウの説明を表示します。

| カード     | ウィンドウ                                                                                       | リセット                                             |
| ---------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| **RPM**    | 1分あたりのリクエスト数 — 60秒のスライディングウィンドウ。                                        | 古いリクエストがウィンドウから抜けていくため、常に変動。 |
| **TPM**    | 1分あたりのトークン数 — 同じスライディングウィンドウをトークンで計上。                            | 常に変動。                                           |
| **週**     | 直近7日間のトークン — あなたのすべてのAPIキーとUIセッションで共有される予算。                      | 1週前の使用がウィンドウから抜けるにつれ、常に変動。     |
| **月**     | 暦月のトークン数。                                                                               | デプロイのタイムゾーンにおける月の境界でリセット。      |

上限に達すると、それ以降のリクエストはモデルインスタンスに到達する前にゲートウェイで`429 Too Many Requests`として拒否され、ウィンドウに空きができるまで続きます。拒否レスポンスの本文は、発動した上限を具体的に示します（`Too many requests per minute`、`Monthly token quota limit reached, reset in usage overview`、`Too many concurrent requests for this model` など）。スライディングおよび暦ウィンドウには、ウィンドウが空くまでの秒数を示す `Retry-After` ヘッダーが付きます。

RPMとTPMは短時間のバーストに対する防壁、週次・月次予算は持続的な消費に対する上限です。1つのリクエストは、影響しうるすべてのウィンドウにカウントされます。APIキーのトラフィックとUIセッションのトラフィックは、同じユーザーレベルの予算を消費します。

## モデル別の同時実行状況 { #concurrency-by-model }

カードの下の表は、利用できる各モデルをデプロイの同時実行上限に対して示します: 各モデルで現在実行中のリクエスト数と、そのモデルの実効上限 — 設定されていれば管理者のモデル別上書き値、なければデプロイのデフォルト。実行数が上限に張り付いているモデルは、`429 Too Many Concurrent Requests` 拒否の発生源です。

## モデルごとの同時実行制限 { #model-concurrency }

レート制限や予算ウィンドウに加え、ゲートウェイはあなたのリクエスト — すべてのAPIキーとセッションを通じて — が1つのモデル上で同時に実行できる数を制限します。デプロイのデフォルトは **1** です。あるモデルへのリクエストが実行中の間、同じモデルへの2つ目の並行リクエストは `429 Too Many Requests` で拒否され、最初のリクエストが終わるまで待たされます。リクエストが完了した瞬間にスロットは解放され、ウィンドウのリセットを待つ必要はありません。そのため、この拒否には `Retry-After` ヘッダーが付きません。

モデルごとに個別にカウントされます。あるモデルの実行中リクエストが他のモデルへのリクエストを妨げることはありません。管理者にはこの制限は適用されません。

デフォルト値とモデルごとの上書き値は、管理者があなたのアカウントに設定します。明示的な上書きがないモデルはデプロイのデフォルトに従い、上書き値 `0` はそのモデルの制限を完全に解除します。

## 数字の由来 { #where-the-numbers-come-from }

- **デプロイのデフォルト** — 管理者が全員に対して設定します：RPM、TPM、月次トークン、モデル別同時実行上限。未設定のデフォルトは、そのウィンドウが制限されないことを意味します。
- **ユーザーレベルの上限** — 管理者があなたのアカウントに設定する週次・月次トークン予算、および RPM と TPM。すべてのキーとセッションで共有されます。

このデプロイでは次のデフォルトを使用します:

| ウィンドウ   | デフォルト                                               |
| ------------ | -------------------------------------------------------- |
| RPM          | 1分あたり 10 リクエスト                                   |
| TPM          | 1分あたり 768,000 トークン                               |
| 月           | ユーザーごとに 1 か月 100,000,000 トークン               |
| 週           | デフォルトなし — 明示的な週次予算を持つアカウントのみ制限 |

内部動作 — ゲートウェイの設定、デフォルト、障害時の挙動、メトリクス — については[Rate Limiting](rate-limiting.md)を参照してください。

## 予算のリセット { #resetting-a-budget }

「週」と「月」のカードには**Reset**ボタンがあります。押すとそのウィンドウのカウンターが直ちにゼロになり、自然な境界を待たずに予算がやり直します。すでに記録された使用量は利用レポートに残ります。リセットはクォータカウンターにのみ影響します。

リセットには理由の入力が必要です。メモは押した記録と一緒に保存され（誰が・いつ・なぜ）、監査履歴から予算がやり直した経緯を追えます。

!!! note

    リセットの対象は週次・月次予算のみです。RPM、TPM、モデル別同時実行上限は短命です — リクエストがウィンドウから抜けるか完了すると、カウンターは自然に解放されます。

### リセット回数の上限 { #reset-quota }

各ウィンドウには2回の無料リセットがあります。回数は押したタイミングに応じて「浮動」します。同じ週に2回リセットすると、次のリセットは暦の境界ではなく、最初の押下から1週間後に再び可能になります。2回とも使い切ると、最も古い押下がウィンドウから抜けるまでボタンは無効化され、無効なボタンにカーソルを合わせると次のリセットが可能になる日付が表示されます。

管理者はこの回数制限を受けません。管理者はいつでも — 自分の予算でも他のユーザーの予算でも — リセットでき、管理者による押下がユーザー自身の2回の無料枠を消費することはありません。
