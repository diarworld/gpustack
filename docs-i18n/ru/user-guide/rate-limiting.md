# Ограничение частоты запросов { #rate-limiting }

GPUStack умеет ограничивать частоту запросов и потребление токенов для каждого
пользователя — на API-шлюзе, до того как трафик дойдёт до модельного инстанса.
Лимиты применяет плагин `gpustack-rate-limit`, работающий на шлюзе Higress;
счётчики хранятся в Redis, поэтому они общие для всех реплик шлюза.

## Как это работает { #how-it-works }

- **Скорость запросов (RPM)** — скользящее минутное окно со счётом в запросах.
- **Скорость токенов (TPM)** — скользящее минутное окно со счётом в токенах,
  которые расходует каждый запрос.
- **Месячный бюджет токенов** — календарный лимит, который сбрасывается 1-го
  числа месяца по часовому поясу деплоя.
- **Недельный бюджет токенов** — скользящее 7-дневное окно.
- **Одновременные запросы к модели** — ограничение на то, сколько запросов
  пользователя может одновременно выполняться на одной модели; слот занимается,
  пока запрос выполняется, и освобождается, когда его стрим заканчивается.

Запрос, превысивший лимит, отклоняется на шлюзе с `429 Too Many Requests`
в формате ошибок OpenAI — ещё до обращения к какому-либо модельному инстансу.
Тело ответа называет сработавший лимит —
`Too many requests per minute`, `Weekly token quota limit reached, reset in
usage overview`, `Too many concurrent requests for this model` — а скользящие
и календарные окна несут заголовок `Retry-After` с числом секунд до
освобождения окна (отклонения по конкурентности заголовка не несут: слот
освобождается с завершением выполняющегося запроса, а не в фиксированный
момент). Отклонённый ответ также несёт заголовок `x-ratelimit-limited-key`
с именем ключа Redis, который вызвал отклонение, — по нему 429 можно
сопоставить с пользователем и окном, которые его породили.

Лимиты считаются **на пользователя**: трафик API-ключей пользователя и его
сессий в интерфейсе расходует один и тот же лимит. Ограничение частоты
применяется только на путях инференса — стандартных эндпоинтах
OpenAI/Anthropic и `/model/proxy`.

## Дефолты деплоя { #deployment-wide-defaults }

Дефолты действуют на всех потребителей, у которых нет собственного явного
лимита. Свежий деплой берёт их из конфиг-файла сервера (YAML-файл, который
сервер загружает через `--config-file` или переменную среды
`GPUSTACK_CONFIG_FILE`):

```yaml
gateway_rate_limit:
  enabled: true
  # Redis is strongly recommended in production: without it the plugin keeps
  # counters per gateway replica, and a multi-replica gateway enforces roughly
  # limit x replicas.
  redis:
    service_name: redis.gpustack-system.svc.cluster.local
    service_port: 6379
  timezone: UTC
  default_rpm: 3
  default_tpm: 768000
  default_monthly_tokens: 100000000
  default_concurrency: 1
```

Дальше дефолты живут в базе данных и редактируются на вкладке
«Использование» → «Лимиты» (**Дефолтные лимиты деплоя**), которая
переопределяет конфиг-файл: сам файл остаётся только стартовым посевом
и источником значений для полей, которые форма оставила пустыми. Пустое
поле в форме (`null` в базе) наследует значение из конфиг-файла, поэтому
деплой может вернуть дефолт в файл без рестарта.

Все поля `default_*`, кроме `default_concurrency`, необязательны: незаданное
поле означает отсутствие лимита такого рода. `default_concurrency` по
умолчанию равен **1** — один выполняющийся запрос на модель на пользователя, —
и не случайно: сбежавший пакетный клиент, удерживающий десятки параллельных
стримов, — именно тот режим отказа, ради которого этот лимит существует.
Поставьте `0`, чтобы отключить лимит конкурентности на весь деплой. Любое
другое поле до настройки ничего не ограничивает. `rejected_code` /
`rejected_msg` по умолчанию отсутствуют, поэтому применяются штатные тексты
отклонения плагина для каждого лимита; явное значение переопределяет их.

### Свободные окна { #free-windows }

Та же форма публикует **свободное окно** для всего деплоя: ежедневный интервал
времени (возможно, переходящий через полночь) плюс полностью свободные дни.
Расписание живёт в конфиге плагина `free_windows` и интерпретируется в
плагиновом `timezone`:

```yaml
free_windows:
  enabled: true
  start: "15:00"        # HH:MM in the plugin-wide timezone
  end: "06:00"          # may wrap past midnight
  days: ["sat", "sun"]  # mon..sun; empty = the daily window every day
```

Внутри расписания плагин приостанавливает все проверки: пропущенные там
запросы не лимитируются, не занимают слотов конкурентности и не добавляют
ничего в счётчики — весь запрос бесплатен, если он **начат** внутри окна,
даже когда стримится дальше его конца. Статистика использования от
`ai-statistics` не затрагивается. Метрика
`gpustack_rate_limit_free_skipped_total` считает пропущенные запросы.
Интерфейс показывает расписание в часовом поясе браузера; сохранённые
значения (и дни) — это настенное время UTC.

Redis должен быть доступен с подов шлюза. Объявите его в McpBridge,
который обслуживает шлюз (или укажите `service_name` на Kubernetes Service,
предварительно задав `global.onlyPushRouteCluster: false` в конфигурации
Higress).

## Лимиты пользователя { #per-user-limits }

Явные лимиты переопределяют дефолты деплоя. Они задаются на учётной записи
пользователя — `rpm_limit`, `tpm_limit`, `weekly_token_limit` и
`monthly_token_limit` — и общие для всех API-ключей пользователя и его
сессий в интерфейсе.

У недельного бюджета нет дефолта на весь деплой: ограничены им только учётные
записи с явным недельным бюджетом. Пользователи без явных лимитов подчиняются
квотам своих групп и дефолтам деплоя — см. [Квоты групп](#group-quotas).

### Конкурентность по моделям { #per-model-concurrency }

Дефолт деплоя `default_concurrency` (1, если деплой не изменил его)
ограничивает, сколько запросов один пользователь может одновременно выполнять
на **одной модели**: второй параллельный запрос к той же модели отклоняется
с 429, пока первый ещё стримится, а запросы к разным моделям идут независимо.
Считаются выполняющиеся запросы, а не скорость: слот занимается, когда запрос
проходит через шлюз, и освобождается, когда его стрим заканчивается, поэтому
завершённый запрос освобождает слот немедленно.

Администраторы от лимита конкурентности освобождены. Переопределения по
моделям задаются на учётной записи через `model_concurrency_limits` —
отображение имени модели в её лимит для этой учётной записи, где `0` означает
явную безлимитность:

```json
{
  "model_concurrency_limits": {
    "glm-5.3-flash": 4,
    "qwen3.8-27b": 2,
    "text-embedding-model": 0
  }
}
```

Модели, отсутствующие в отображении, наследуют `default_concurrency`.
Администратор может править отображение для каждого пользователя в панели
настроек пользователя; изменения вступают в силу в течение одного прохода
реконсилера (по умолчанию 30 секунд).

!!! note "Примечание"

    Слот, чьё освобождение потерялось — например, при падении шлюза посреди
    стрима, — автоматически возвращается через час (`concurrency_stale_seconds`
    у плагина, настраивается через `gateway_rate_limit.plugin_config`),
    поэтому упавший стрим не может заблокировать слот пользователя навсегда.

Изменения вступают в силу в течение одного прохода реконсилера (по умолчанию
30 секунд, см. `GPUSTACK_GATEWAY_RATE_LIMIT_RECONCILE_INTERVAL_SECONDS`).

!!! note "Примечание"

    Лимиты частоты применяются на шлюзе, поэтому действуют на трафик,
    приходящий через него. Вызовы инференса напрямую на API-порт сервера
    не лимитируются.

## Квоты групп { #group-quotas }

Группы несут те же поля лимитов, что и учётные записи, — RPM, TPM, недельный
и месячный бюджеты токенов и лимиты выполняющихся запросов по моделям; задаются
на странице «Управление доступом» → «Группы» кнопкой **Управлять лимитами**.
Лимит группы никогда не ограничивает группу как целое: действующие лимиты
участника **разрешаются по каждому полю отдельно**, с таким приоритетом:

1. явный лимит пользователя — задан на учётной записи, выигрывает в обе
   стороны;
2. иначе — наименьшее значение среди групп пользователя (включая вложенные
   подгруппы). Лимит группы и ужесточает, и ослабляет дефолты деплоя — дать
   одной команде RPM выше, чем у всех, вполне законно;
3. иначе — дефолты на весь деплой.

Например, при `default_rpm: 100` и участнике одной группы с лимитом RPM 10
и другой с RPM 2 пользователь без явных лимитов работает на RPM 2, а — если
те же группы ограничивают TPM на 1000 и 10000 — на TPM 1000: каждое поле
разрешается само по себе. Если учётная запись явно задаёт RPM 30,
применяется 30, что бы ни говорили группы. У недельного бюджета нет дефолта
на весь деплой, поэтому он берётся из строки пользователя, наименьшего
значения по группам — или отсутствует.

Групповые лимиты по моделям разрешаются по одной модели за раз: выигрывает
собственная запись `model_concurrency_limits` пользователя (сохранённый `0` —
явная безлимитность); иначе применяется наименьший ненулевой лимит среди групп
участника; иначе `default_concurrency`. `0` у **группы** означает «эта группа
не ограничивает модель» — такое значение никогда не участвует в сравнении,
поэтому не может ни ужесточить дефолт деплоя, ни отменить лимит соседней
группы.

Разрешение происходит на сервере: плагин шлюза продолжает получать одну
комбинацию на пользователя с уже разрешёнными числами и групп никогда
не видит. Правка квоты или смена членства (пользователь вошёл в группу или
покинул её) подхватывается в течение одного прохода реконсилера (по умолчанию
30 секунд). Страница «Использование» и эндпоинт `GET /v2/usage/rate-limits`
сообщают разрешённые значения — те самые числа, которые реально применяются.

## Поведение при сбоях { #failure-behaviour }

Лимитер отказывает открыто: если Redis недоступен, запросы пропускаются,
а в лог пишется предупреждение — трафик не блокируется из-за проблем
собственной инфраструктуры лимитера. Следите за счётчиками отклонений
в разделе «Метрики» ниже — по ним видно, что лимиты действительно применяются.

## Текущие лимиты и использование { #current-limits-and-usage }

Сервер отдаёт то, что шлюз применяет прямо сейчас, на эндпоинте
`GET /v2/usage/rate-limits`. Любой аутентифицированный пользователь по
умолчанию получает свою картину; платформенный администратор (администратор
без привязки к Org — тот же барьер, что маршруты использования применяют
к межтенантным просмотрам) может передать `user_id` и посмотреть любого
пользователя, все остальные молча получают только свой срез.

Ответ несёт:

- `mode` — `redis` (живые счётчики, читаются из Redis в момент запроса),
  `local` (лимитирование включено без Redis, поэтому лимиты возвращаются
  без счётчиков) или `disabled` (функция выключена; страница «Использование»
  скрывает раздел).
- `user` — недельный и месячный бюджеты токенов пользователя (какие заданы),
  каждый с живым окном, плюс `model_concurrency` — лимиты выполняющихся
  запросов по моделям, заданные на учётной записи (`model_concurrency_limits`),
  каждый с живым счётчиком занятых слотов `running`. Детализируются только
  явно названные модели; администраторы (освобождены) и пользователи без
  переопределений получают пустой список. `concurrency_default` несёт дефолт
  деплоя, который наследуют остальные модели (`null`, когда лимит выключен).
- `generated_at` — момент, в который были прочитаны все окна.
- `usage_error` — заполняется только при неудаче чтения Redis и несёт лишь
  имя класса исключения, никогда его сообщение (в нём могут быть имена
  хостов).

Поля без значения опускаются, а не отправляются как `null`: в режиме `local`
или всякий раз, когда Redis недоступен, у окна просто нет `used`. Чтение
отказывает открыто — лимиты возвращаются всегда. Вкладка «Сводка» страницы
«Использование» рендерит этот ответ как раздел **Лимиты**.

Для деплоя с дефолтами 3 RPM, 768000 TPM и 100000000 месячных токенов
и пользователя с недельным бюджетом 100000:

```json
{
  "mode": "redis",
  "generated_at": "2026-11-19T10:30:00Z",
  "user": {
    "weekly_limit": 100000,
    "concurrency_default": 1,
    "windows": [
      {"kind": "query", "period": "60s", "window_seconds": 60, "limit": 3, "used": 2, "reset_seconds": 41},
      {"kind": "token_rolling", "period": "60s", "window_seconds": 60, "limit": 768000, "used": 4820, "reset_seconds": 27},
      {"kind": "token_calendar", "period": "each_month", "limit": 100000000, "used": 210000, "reset_seconds": 999000},
      {"kind": "token_rolling", "period": "604800s", "window_seconds": 604800, "limit": 100000, "used": 37215, "reset_seconds": 172800}
    ],
    "model_concurrency": []
  }
}
```

Каждое окно считается на пользователя: трафик API-ключей и трафик интерфейса
расходуют один и тот же лимит, поэтому оба читают один и тот же счётчик.
У календарных окон нет `window_seconds` — их длина следует календарю, а их
`reset_seconds` отсчитывает время до границы по часовому поясу деплоя.

### Восстановление счётчиков { #counter-recovery }

Счётчики Redis плагина — единственное состояние применения лимитов: когда
rate-limit Redis их теряет — свежий инстанс, отказоустойчивое переключение,
сброс без персистентности, — календарные квоты стартуют с нуля, а пользователи,
уже потратившие дневной / недельный / месячный бюджет, получают его обратно
до конца окна. Чтобы закрыть эту брешь, сервер переигрывает потребление,
уже записанное в `model_usage_details`, ровно в те счётчики, которые читает
плагин, — и только в ещё не существующие счётчики: живой счётчик никогда
не трогается. Проход выполняется по циклу (каждые 5 минут): каждый цикл
проверяет счётчики одним конвейерным EXISTS, а сканирование деталей
запускается, только когда чего-то действительно не хватает, поэтому сброс
Redis залечивается сам в течение одного интервала.

Неточно по замыслу:

- Минутные окна не восстанавливаются — они старятся за 60 секунд, задолго
  до того, как восстановление успеет что-то значить.
- Восстановленные составляющие — почасовые агрегаты, поэтому скользящая
  неделя распадается шагами по часу, а не по запросу.
- Плагин считает на шлюзе, а сервер записывает на прокси, поэтому прерванные
  или неучтённые запросы могут увести восстановленный итог чуть в сторону
  от потерянного.

Включение персистентности (AOF / RDB) на rate-limit Redis полностью
исключает восстановление.

!!! note "Примечание"

    Эндпоинт и восстановитель работают с тем же Redis, в который шлюз пишет
    счётчики, — `gateway_rate_limit.redis`, — а не с верхнеуровневым
    `redis_url` сервера.

### Сброс бюджета { #resetting-a-budget }

Карточки недельного и месячного бюджетов на странице «Использование» несут
кнопку сброса: нажатие удаляет счётчики пользователя этого вида окна, поэтому
бюджет стартует с нуля посреди окна, не дожидаясь естественной границы.
Каждое нажатие записывается в `gateway_rate_limit_resets` — примечание
с причиной обязательно и попадает в строку вместе с пользователем, датой
нажатия и, когда администратор нажал за кого-то, тем, кто это сделал.

На каждое окно приходятся два бесплатных нажатия; квота плывёт вместе
с самими нажатиями — два сброса в течение одной недели делают следующий
доступным через неделю после первого нажатия, а не на следующей календарной
границе. Когда оба израсходованы, кнопка становится неактивной, пока самое
старое нажатие не выйдет из окна. Платформенный администратор квотой
не ограничен: его нажатия (своего бюджета или бюджета другого пользователя)
записываются, но никогда не расходуют собственный лимит пользователя.

Пересборка счётчиков сотрудничает со сбросами: потребление, записанное до
последнего сброса вида окна, прощается, поэтому пересборка после потери
Redis продолжается от сброса, а не воскрешает прощённый расход.

Расписание свободных окон учитывается так же: плагин пропускает запросы
внутри окна, не считая их, поэтому строки, записанные после запуска
расписания (создания строки настроек), чей запрос начался внутри него,
из переигрывания исключаются — иначе каждый рестарт сервера вносил бы
свободное время обратно в бюджеты. Выключенное расписание не исключает
ничего.

## Метрики { #metrics }

Плагин объявляет три счётчика на каждое решение лимитера:

- `gpustack_rate_limit_request_total` — запросы, прошедшие проверки лимитов,
  разбитые на `result="passed"` и `result="limited"`.
- `gpustack_rate_limit_rejected_total` — отклонённые запросы с атрибуцией
  к комбинации и окну, вызвавшим отклонение.
- `gpustack_rate_limit_value_total` — расход, записанный в каждый бакет окна
  (1 на запрос для окон запросов и захватов конкурентности, число токенов
  для токенных окон).

Плагин статистики Higress AI сплавляет их в маршрутные метрики Envoy,
поэтому на Prometheus-эндпоинте шлюза они доступны с префиксом
`route_upstream_model_consumer_metric_`, где комбинация и окно сплющены
в имя, а AI-размерности приложены метками:

```promql
route_upstream_model_consumer_metric_gpustack_rate_limit_request_total_rule_gpustack_rate_limit_result_passed{ai_route="ai-route-route-1.internal",ai_cluster="outbound_80__model-1-46.static",ai_model="glm-5.3-flash",ai_consumer="a3d73e9f0c402120.gpustack-6"}
```

- `ai_consumer` — аутентифицированный потребитель, например
  `a3d73e9f0c402120.gpustack-6`.
- `ai_route`, `ai_cluster`, `ai_model` — AI-маршрут и инстанс модели,
  к которым шёл запрос.
- Комбинация и окно становятся сегментами имени (не-алфанумерические символы
  сплющиваются в `_`):
  `..._rejected_total_rule_gpustack_rate_limit_combo_<combination>_kind_<query|token_rolling|token_calendar>_period_<60s|604800s|each_day|each_month>_bucket_consumer_<consumer>`.

Счётчики экспортируются подами шлюза на `:15020/stats/prometheus`; на подах
стоят стандартные аннотации `prometheus.io/scrape: "true"`,
`prometheus.io/port: "15020"` и `prometheus.io/path: "/stats/prometheus"`,
поэтому Prometheus, соскребающий аннотации подов, подхватывает их.

### Сокращение имён с помощью relabeling { #shortening-the-names-with-relabeling }

У статистики Envoy нет размерностей меток — плагин может закодировать их
только в имени статистики, и именно AI-скелет префикса заставляет встроенные
bootstrap-экстракторы Higress производить метки `ai_*`. Конфигурация
экстрактора на стороне кластера зафиксирована в этой версии Higress (патч
EnvoyFilter BOOTSTRAP не учитывается), поэтому способ получить короткие имена
с идентификаторами в метках — `metric_relabel_configs` на стороне Prometheus.
Применённые к job соскребания шлюза, эти правила превращают имена выше в
`gpustack_rate_limit_{request,rejected,value}_total` с метками
`rl_combo` / `rl_kind` / `rl_period` / `rl_bucket` / `rl_result`:

```yaml
metric_relabel_configs:
  # ids out of the flattened name, into labels — these rules read the
  # ORIGINAL name, so they must come before the rename below.
  - source_labels: [__name__]
    regex: .*gpustack_rate_limit_request_total_rule_.*_result_(.+)
    target_label: rl_result
  - source_labels: [__name__]
    regex: .*_combo_(.+?)_kind_.*
    target_label: rl_combo
  - source_labels: [__name__]
    regex: .*_kind_(.+?)_period_.*
    target_label: rl_kind
  - source_labels: [__name__]
    regex: .*_period_(.+?)_bucket_consumer_.*
    target_label: rl_period
  - source_labels: [__name__]
    regex: .*_bucket_consumer_(.+)
    target_label: rl_bucket
  # shorten the name last
  - source_labels: [__name__]
    regex: route_upstream_model_consumer_metric_(gpustack_rate_limit_(?:request|rejected|value)_total).*
    target_label: __name__
    replacement: ${1}
```

Примеры запросов в терминах переименованных метрик:

```promql
# rejections per consumer
sum by (ai_consumer) (rate(gpustack_rate_limit_rejected_total[5m]))

# which combination and window produce them
sum by (rl_combo, rl_kind, rl_period) (rate(gpustack_rate_limit_rejected_total[5m]))

# enforcement sanity: rejected share of checked requests
sum (rate(gpustack_rate_limit_request_total{rl_result="limited"}[5m]))
/
sum (rate(gpustack_rate_limit_request_total[5m]))
```

!!! note "Примечание"

    На Higress 2.1.x с включённым плагином статистики AI «голых» имён
    `gpustack_rate_limit_*` в сыром экспорте не существует — они появляются
    только после описанного выше relabeling. Без него всегда запрашивайте
    через префикс `route_upstream_model_consumer_metric_`. Для того, что
    посчитано внутри каждого окна прямо сейчас, источником истины служат
    ключи Redis, названные в `x-ratelimit-limited-key`.

## События реконсилера { #reconciler-events }

Сервер запускает реконсилер, который следит за таблицами API-ключей,
принципалов, членства и настроек и перепубликует CR WasmPlugin лимитов
частоты в течение одного прохода реконсилера (по умолчанию 30 секунд,
`GPUSTACK_GATEWAY_RATE_LIMIT_RECONCILE_INTERVAL_SECONDS`). Его события
и строки лога несут тег источника `gateway_rate_limit_reconciler`
(например `gateway_rate_limit_reconciler.api_key`). Этот тег помечает
источник события, а не метрику Prometheus — сам реконсилер метрик
не экспортирует. Если он виден в журнале событий, значит изменение лимита
было подхвачено и доставлено на шлюз.
